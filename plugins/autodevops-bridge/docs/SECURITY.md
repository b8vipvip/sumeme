# Security model

## Threat model

AutoDevOps Bridge assumes repository content, issues, pull requests, workflow logs, service logs, and status snapshots may contain malicious or misleading text. They are data, not trusted instructions.

The primary risks are:

- prompt injection through repository or log content;
- excessive GitHub token permissions;
- unauthorized workflow dispatch;
- leaking secrets through diagnostics;
- exposing an unrestricted production shell;
- cross-project or cross-user data access;
- unsafe rollback around database migrations.

## Controls

### No unrestricted shell

The MCP server has no `run_shell`, `ssh`, `exec`, or arbitrary workflow-name tool. It can call only workflow file names stored in the server-side project registry.

### Least-privilege GitHub access

For private MVP testing, use a fine-grained GitHub token restricted to explicitly selected repositories. Grant only the repository content and Actions permissions required for status reads and workflow dispatch.

For public multi-user release, replace the shared token with per-user OAuth authorization and encrypted tenant-scoped storage.

### Sanitized status boundary

ChatGPT reads `ops-status/status/status.json`, generated by a trusted runner-side collector. The snapshot must not include:

- `.env` contents;
- API keys or bearer tokens;
- private keys or certificates;
- cookies or session IDs;
- database connection strings;
- full user documents or personal memory contents;
- unrestricted raw logs.

### Write-action controls

- Deployment triggers only an allow-listed workflow.
- Diagnostics use bounded inputs and an allow-listed service name enforced by the target workflow.
- Rollback requires literal `ROLLBACK` confirmation and is marked destructive.
- Production workflows should use concurrency locks and trusted branches/SHAs.

### Transport security

- Public mode must be behind HTTPS.
- The private HTTP MVP supports a bearer secret and Host allow-list.
- Public mode must implement OAuth 2.1, PKCE, audience/resource validation, token expiry and revocation.

### Auditability

All production actions run as GitHub Actions workflows, preserving actor, commit, inputs, timestamps, logs and results in GitHub's audit trail.

## Operational recommendations

- Keep managed repositories private when a persistent self-hosted runner has production access.
- Use a dedicated non-root runner account.
- Limit sudo to reviewed scripts, or avoid sudo entirely by granting only the minimum container/runtime group access.
- Do not allow untrusted fork pull requests to run on the production runner.
- Protect production workflow files and the project registry.
- Pin third-party actions to reviewed commit SHAs before public release.
- Set log retention, backup retention and Docker image cleanup policies.
- Alert on disk pressure, repeated service restarts, failed deployments and stale status snapshots.

## Incident response

1. Disable or remove the affected project from the server registry.
2. Revoke the GitHub token or OAuth grant.
3. Stop the MCP service if unauthorized calls are suspected.
4. Inspect GitHub workflow audit history.
5. Rotate any potentially exposed credentials.
6. Restore a trusted release through the reviewed rollback process.
7. Document the incident and add a regression test before restoring access.
